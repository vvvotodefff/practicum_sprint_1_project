## Хорошие практики

Все пять пунктов выполнены:

- Отдельный проект `ProjectWork.IntegrationTests` (имя соответствует основному проекту).
- Fixture реализует `IAsyncLifetime` и управляет запуском/удалением контейнера.
- Один PostgreSQL-контейнер на коллекцию, сброс временной БД перед каждым тестом.
- Изоляция: новый scope для каждого теста, непараллельная коллекция, отсутствие
  фонового обработчика API в интеграционных тестах и зависимости от рабочей БД.
- Проверяются обновление, удаление, отсутствующие записи, комбинации фильтров,
  пагинация, ошибки ограничений и откат транзакций, а не только успешное добавление.

## Критерии «Отлично»

- Тесты имеют явные комментарии Arrange / Act / Assert;
  короткие проверки исключений используют объединённый Act / Assert.
- Проверяются связи, каскадное удаление средствами PostgreSQL, обязательность
  столбцов, первичные ключи, длины строк, ограничения дат и количества мест.
- Репозитории содержат доступ к данным, а не правила резервирования/смены статусов.
- История логически разделена: подготовка, репозитории с миграцией,
  интеграционные тесты, итоговая документация. Небольшое отличие от буквального
  примера задания: репозитории и миграция находятся в одном коммите `8cc7712`,
  а не в двух. Ради этого история не переписывалась.

## Проверка API

Через настоящий интерфейс Swagger UI в Chrome, кнопками `Try it out` и `Execute`
(браузерная автоматизация с отдельным временным профилем), проверены:

| Операция | Фактический ответ |
|---|---|
| POST /events | 201, создано событие с тремя свободными местами |
| POST /events/{id}/book | 202, создана бронь Pending |
| GET /events/{id} | 200, свободных мест стало два |
| GET /bookings/{id} | 200, бронь связана с созданным событием |

Дополнительно `scripts/Verify-Api.ps1` успешно проверил все семь операций
в Swagger JSON, HTTP-валидацию, CRUD, SQL-фильтры и пагинацию,
20 одновременных бронирований на 5 мест (5 ответов 202, 15 ответов 409),
перезапуск с сохранением данных, фоновое подтверждение брони и каскадное удаление.
Все созданные этими проверками события и брони удалены; временные API остановлены.
Контейнеры интеграционных тестов удалены, учебный `eventapi-postgres` сохранён.

## Воспроизведение

```shell
docker compose up -d --wait postgres
dotnet build ProjectWork.slnx --no-incremental
dotnet test ProjectWork.slnx --no-build --logger trx --results-directory TestResults/stage6-first
dotnet test ProjectWork.slnx --no-build --logger trx --results-directory TestResults/stage6-repeat

dotnet ef migrations has-pending-model-changes --project ProjectWork.csproj --startup-project ProjectWork.csproj
```

TRX-отчёты сохраняются в игнорируемом каталоге `TestResults`, не в исходниках.
Ручной сценарий Swagger приведён в корневом README.

## Неблокирующие замечания

- Полная сборка выдаёт 51 предупреждение: 50 `CS1591` о недостающей XML-документации
  публичных членов и одно `xUnit2031` об использовании `Assert.Single` с `Where`.
  Они не подавлялись и не являются ошибками сборки.
- Глобальный `dotnet-ef` на проверочной машине — 10.0.9, пакеты EF Core — 10.0.12.
  CLI-проверки проходят, но инструмент предупреждает о старой версии.
  README содержит команду обновления до 10.0.12; глобальный инструмент не менялся.
- При запуске только на HTTP middleware HTTPS пишет предупреждение об отсутствии
  HTTPS-порта. Проверенные HTTP-эндпоинты работают; HTTPS-профиль описан в README.
- Защита мест через `SemaphoreSlim` действует внутри одного процесса API.
  Горизонтальное масштабирование потребует отдельной защиты на уровне БД;
  это ограничение текущей учебной реализации, не требование шестого спринта.
