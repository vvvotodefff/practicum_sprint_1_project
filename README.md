# Сервис для управления мероприятиями

Учебный проект: REST API для создания, просмотра, обновления и удаления событий.
Приложение разработано на ASP.NET Core Web API, данные хранятся в памяти во время работы приложения.
Во втором спринте добавлены: глобальная обработка ошибок через middleware, фильтрация и пагинация событий, юнит-тесты.

## Технологии

- C# и .NET 10
- ASP.NET Core Web API
- Dependency Injection
- Swagger / OpenAPI
- Data Annotations и автоматическая валидация моделей
- Problem Details для единого формата ошибок
- Middleware для глобальной обработки исключений
- xUnit для юнит-тестов

## Запуск проекта

Для запуска необходим [.NET SDK 10](https://dotnet.microsoft.com/download/dotnet/10.0) или более поздняя совместимая версия.

1. Клонируйте репозиторий:

   ```bash
   git clone https://github.com/vvvotodefff/practicum_sprint_1_project.git
   cd practicum_sprint_1_project
   ```

2. Восстановите зависимости и соберите проект:

   ```bash
   dotnet restore
   dotnet build
   ```

3. Запустите приложение:

   ```bash
   dotnet run
   ```

После запуска API по умолчанию доступно по адресам:

- `http://localhost:5259`
- `https://localhost:7167`

Swagger UI доступен по адресу `http://localhost:5259/swagger`.

## API

| Метод | Маршрут | Описание | Успешный ответ |
|---|---|---|---|
| `GET` | `/events` | Получить события с фильтрацией и пагинацией | `200 OK` |
| `GET` | `/events/{id}` | Получить событие по идентификатору | `200 OK` |
| `POST` | `/events` | Создать событие | `201 Created` |
| `PUT` | `/events/{id}` | Полностью обновить событие | `204 No Content` |
| `DELETE` | `/events/{id}` | Удалить событие | `204 No Content` |

Для отсутствующего события операции `GET`, `PUT` и `DELETE` возвращают `404 Not Found` в формате Problem Details.

### Фильтрация и пагинация `GET /events`

Все параметры передаются в строке запроса и являются необязательными. Фильтры работают совместно (логическое И).

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `title` | string | — | Поиск по названию: без учёта регистра, частичное совпадение |
| `from` | DateTime | — | События, которые начинаются не раньше указанной даты |
| `to` | DateTime | — | События, которые заканчиваются не позже указанной даты |
| `page` | int | `1` | Номер страницы, начиная с 1 |
| `pageSize` | int | `10` | Количество элементов на странице |

Пример запроса:

```
GET /events?title=встреча&from=2026-07-01T00:00:00&to=2026-07-31T23:59:59&page=1&pageSize=10
```

Ответ возвращается в виде страницы результатов:

```json
{
  "totalCount": 12,
  "page": 1,
  "pageSize": 10,
  "items": [ /* события текущей страницы */ ]
}
```

`totalCount` — общее количество событий, подходящих под фильтры (до разбиения на страницы).

## Формат ответа при ошибках

Все ошибки возвращаются в едином формате [Problem Details (RFC 7807)](https://datatracker.ietf.org/doc/html/rfc7807).
Необработанные исключения перехватываются глобальным middleware `ExceptionHandlingMiddleware`, ошибки логируются через `ILogger`.

| Статус | Когда возникает |
|---|---|
| `400 Bad Request` | Ошибки валидации: некорректное тело запроса, неверные параметры пагинации |
| `404 Not Found` | Событие с указанным идентификатором не найдено |
| `500 Internal Server Error` | Непредвиденная ошибка сервера |

Пример ответа при ошибке `404`:

```json
{
  "title": "Ресурс не найден",
  "status": 404,
  "detail": "Событие с идентификатором '11111111-1111-1111-1111-111111111111' не найдено."
}
```

При ошибках валидации (`400`) дополнительно возвращается объект `errors` со списком проблемных полей.

### Пример события

```json
{
  "title": "Встреча команды",
  "description": "Пиво в честь окончания первого спринта",
  "startAt": "2026-06-22T12:00:00",
  "endAt": "2026-06-22T13:00:00"
}
```

Идентификатор `id` создаётся сервером автоматически при выполнении `POST /events`.

## Валидация

Для создания и обновления события действуют следующие правила:

- `title` — обязательное поле;
- `startAt` — обязательное поле;
- `endAt` — обязательное поле;
- `endAt` должно быть позже `startAt`.

При нарушении правил API автоматически возвращает `400 Bad Request` с описанием ошибок в формате Validation Problem Details.

## Тесты

Юнит-тесты написаны на xUnit и находятся в проекте `ProjectWork.Tests`.
Они покрывают CRUD-операции, фильтрацию, пагинацию и валидацию модели события.

Запуск всех тестов из корня репозитория:

```bash
dotnet test
```

## Структура проекта

```text
Controllers/        — REST-контроллеры и обработка HTTP-запросов
Exceptions/         — собственные типы исключений
Middleware/         — глобальная обработка исключений
Models/             — модели данных и правила валидации

ProjectWork.Tests/  — юнит-тесты (xUnit)

```

## Особенности хранения данных

События хранятся в коллекции `List<Event>` в памяти приложения. После остановки или перезапуска приложения созданные данные удаляются.
