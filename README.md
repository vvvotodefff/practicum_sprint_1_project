# Сервис для управления мероприятиями

Учебный проект: REST API для создания, просмотра, обновления и удаления событий, а также бронирования мест на них.
Приложение разработано на ASP.NET Core Web API, данные хранятся в памяти во время работы приложения.
Во втором спринте добавлены: глобальная обработка ошибок через middleware, фильтрация и пагинация событий, юнит-тесты.
В третьем спринте добавлены: бронирование событий и фоновая обработка броней.
В четвёртом спринте добавлены: ограничение мест на событии, защита от овербукинга и параллельная фоновая обработка.

## Технологии

- C# и .NET 10
- ASP.NET Core Web API
- Dependency Injection
- Swagger / OpenAPI
- Data Annotations и автоматическая валидация моделей
- Problem Details для единого формата ошибок
- Middleware для глобальной обработки исключений
- BackgroundService для фоновой обработки бронирований
- DTO для отделения контракта API от моделей хранения
- Примитивы синхронизации: `lock`, `SemaphoreSlim`, `ConcurrentDictionary`
- xUnit для юнит-тестов

## Запуск проекта

Для запуска необходим [.NET SDK 10](https://dotnet.microsoft.com/download/dotnet/10.0) или более поздняя совместимая версия.

1. Клонируйте репозиторий:

   ```bash
   git clone https://github.com/vvvotodefff/practicum_sprint_1_project.git
   cd practicum_sprint_1_project
   ```

2. Восстановите зависимости и соберите проект:

   ```bash
   dotnet restore
   dotnet build
   ```

3. Запустите приложение:

   ```bash
   dotnet run
   ```

После запуска API по умолчанию доступно по адресам:

- `http://localhost:5259`
- `https://localhost:7167`

Swagger UI доступен по адресу `http://localhost:5259/swagger`.

## API

| Метод | Маршрут | Описание | Успешный ответ |
|---|---|---|---|
| `GET` | `/events` | Получить события с фильтрацией и пагинацией | `200 OK` |
| `GET` | `/events/{id}` | Получить событие по идентификатору | `200 OK` |
| `POST` | `/events` | Создать событие | `201 Created` |
| `PUT` | `/events/{id}` | Полностью обновить событие | `204 No Content` |
| `DELETE` | `/events/{id}` | Удалить событие | `204 No Content` |
| `POST` | `/events/{id}/book` | Создать бронь на событие | `202 Accepted` |
| `GET` | `/bookings/{id}` | Получить текущее состояние брони | `200 OK` |

### Модель события

| Поле | Тип | Описание |
|---|---|---|
| `id` | Guid | Идентификатор события, присваивается сервером |
| `title` | string | Название события, обязательное |
| `description` | string? | Описание события |
| `startAt` | DateTime | Время начала, обязательное |
| `endAt` | DateTime | Время окончания, должно быть позже начала |
| `totalSeats` | int | Общее количество мест. Обязательное, должно быть больше нуля |
| `availableSeats` | int | Текущее количество свободных мест. Считает сервер |

Клиент не может задать `id` и `availableSeats`: тела запросов описаны отдельными DTO
(`CreateEvent` для создания и `UpdateEvent` для обновления), в которых этих полей просто нет.
При создании события `availableSeats` равно `totalSeats`; дальше значение уменьшается при
каждой успешной брони и возрастает, когда бронь отклоняется и место возвращается в пул.

При обновлении события через `PUT` количество свободных мест **пересчитывается сервером** так,
чтобы уже занятые места сохранились: если в зале на 100 мест занято 40, а вместимость увеличили
до 150, свободных станет 110. Уменьшить вместимость ниже числа занятых мест нельзя — вернётся `400`.

Для отсутствующего события операции `GET`, `PUT` и `DELETE` возвращают `404 Not Found` в формате Problem Details.

### Фильтрация и пагинация `GET /events`

Все параметры передаются в строке запроса и являются необязательными. Фильтры работают совместно (логическое И).

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `title` | string | — | Поиск по названию: без учёта регистра, частичное совпадение |
| `from` | DateTime | — | События, которые начинаются не раньше указанной даты |
| `to` | DateTime | — | События, которые заканчиваются не позже указанной даты |
| `page` | int | `1` | Номер страницы, начиная с 1 |
| `pageSize` | int | `10` | Количество элементов на странице |

Пример запроса:

```
GET /events?title=встреча&from=2026-07-01T00:00:00&to=2026-07-31T23:59:59&page=1&pageSize=10
```

Ответ возвращается в виде страницы результатов:

```json
{
  "totalCount": 12,
  "page": 1,
  "pageSize": 10,
  "items": [ /* события текущей страницы */ ]
}
```

`totalCount` — общее количество событий, подходящих под фильтры (до разбиения на страницы).

## Бронирование событий

### Модель `Booking`

| Поле | Тип | Описание |
|---|---|---|
| `id` | Guid | Уникальный идентификатор брони, присваивается сервером |
| `eventId` | Guid | Идентификатор события, к которому относится бронь |
| `status` | BookingStatus | Текущий статус брони |
| `createdAt` | DateTime | Время создания брони |
| `processedAt` | DateTime? | Время обработки брони. Пока бронь не обработана — `null` |

### Статусы брони

| Статус | Описание |
|---|---|
| `Pending` | Бронь создана и ожидает обработки |
| `Confirmed` | Бронь подтверждена |
| `Rejected` | Бронь отклонена |

В JSON статус передаётся строкой, например `"status": "Pending"`.

### `POST /events/{id}/book`

Создаёт бронь для указанного события. Обработка выполняется асинхронно, поэтому эндпоинт сразу
возвращает `202 Accepted` и не ждёт результата. Ссылка на созданную бронь возвращается в заголовке `Location`:

```
Location: http://localhost:5259/bookings/0062f294-f29b-4241-8c7c-0ac0e1f566ba
```

Тело ответа:

```json
{
  "id": "0062f294-f29b-4241-8c7c-0ac0e1f566ba",
  "eventId": "eb99a16f-ab16-464e-bf3b-b72d1967709e",
  "status": "Pending",
  "createdAt": "2026-08-11T10:45:42.0499777Z",
  "processedAt": null
}
```

Возможные ошибки:

| Статус | Когда возникает |
|---|---|
| `404 Not Found` | События с указанным идентификатором не существует |
| `409 Conflict` | На событии не осталось свободных мест |

Место занимается **в момент создания брони**, а не при её обработке — поэтому клиент сразу
узнаёт, досталось ли ему место. Ответ при исчерпании мест:

```json
{
  "title": "Нет свободных мест",
  "status": 409,
  "detail": "No available seats for this event"
}
```

### `GET /bookings/{id}`

Возвращает текущее состояние брони: `200 OK` с телом того же вида, что и выше.
Если брони с указанным идентификатором нет — `404 Not Found`.

### Фоновая обработка бронирований

За обработку отвечает `BookingProcessingService` — фоновый сервис на базе `BackgroundService`,
зарегистрированный через `AddHostedService`. Он работает всё время, пока запущено приложение:

1. раз в секунду (`PollInterval`) опрашивает хранилище и выбирает брони со статусом `Pending`;
2. запускает обработку всех выбранных броней **одновременно** через `Task.WhenAll`;
3. для каждой брони выдерживает паузу в 2 секунды (`ProcessingDelay`) — имитация обращения
   к внешней системе;
4. проверяет, существует ли событие: если его удалили, пока бронь ждала очереди, бронь
   переводится в `Rejected` с записью в лог уровня `Warning`;
5. иначе переводит бронь в `Confirmed` и заполняет `processedAt`;
6. при непредвиденной ошибке отклоняет бронь и **возвращает место в пул** через `ReleaseSeats`.

Благодаря параллельному запуску десять броней обрабатываются за те же две секунды, что и одна:
последовательная версия потратила бы двадцать.

### Синхронизация

Данные лежат в памяти, и к ним одновременно обращаются два независимых источника: HTTP-запросы
и фоновый сервис. Поэтому в проекте используются три разных примитива — каждый решает свою задачу.

| Примитив | Где | Зачем |
|---|---|---|
| `lock` | `EventService` | Поиск события и изменение счётчика мест должны быть одной неделимой операцией. Без этого два потока могут одновременно пройти проверку «место есть» и продать одно место дважды |
| `lock` | `BookingService.CreateBookingAsync` | Критическая секция «занять место → создать бронь»: бронь появляется только после того, как место закреплено |
| `SemaphoreSlim` | `BookingProcessingService` | Асинхронный аналог `lock`: внутри `lock` нельзя использовать `await`, а фоновой обработке это необходимо. Пропускает к записи одну задачу за раз |
| `ConcurrentDictionary` | Хранилище броней | Потокобезопасная коллекция: чтение и добавление броней не требуют блокировок вообще |

Два важных момента:

- **Задержка выполняется до захвата семафора.** Если захватить семафор первым, задачи выстроятся
  в очередь и параллельность исчезнет. Под семафором находится только быстрая запись результата.
- **Порядок захвата блокировок всегда один**: сначала замок броней, затем замок событий.
  Обратного пути в коде не существует, поэтому взаимная блокировка (deadlock) невозможна.

Потокобезопасная коллекция не заменяет `lock`: она гарантирует целостность самой коллекции,
но не атомарность последовательности операций над разными объектами.

### Пример сценария использования

1. Создать событие:

   ```bash
   curl -X POST http://localhost:5259/events \
     -H "Content-Type: application/json" \
     -d '{"title":"Концерт","startAt":"2026-09-01T19:00:00","endAt":"2026-09-01T22:00:00","totalSeats":3}'
   ```

   В ответе — `201 Created` и событие с присвоенным `id`, `totalSeats: 3` и `availableSeats: 3`.

2. Забронировать место на событии (подставьте `id` из первого шага):

   ```bash
   curl -i -X POST http://localhost:5259/events/{eventId}/book
   ```

   В ответе — `202 Accepted`, заголовок `Location` и бронь со статусом `Pending`.

3. Сразу запросить состояние брони:

   ```bash
   curl http://localhost:5259/bookings/{bookingId}
   ```

   Статус ещё `Pending`, `processedAt` равен `null`.

4. Подождать несколько секунд и повторить запрос из шага 3 — статус изменится на `Confirmed`,
   а в `processedAt` появится время обработки.

### Пример: защита от овербукинга

Событие из первого шага рассчитано на три места. Забронируем его четыре раза:

```bash
for i in 1 2 3 4; do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:5259/events/{eventId}/book
done
```

Результат:

```
202
202
202
409
```

Первые три брони заняли все места, четвёртая получила `409 Conflict` с телом
`"No available seats for this event"`. У события при этом `availableSeats: 0`.

То же самое происходит и при одновременных запросах: если отправить на событие с тремя местами
двадцать параллельных запросов, ровно три вернут `202`, а семнадцать — `409`, и счётчик мест
не уйдёт в минус. За это отвечает критическая секция в `BookingService.CreateBookingAsync`:
проверка свободных мест и создание брони выполняются как одна неделимая операция.
Поведение зафиксировано тестом `ConcurrentBookings_DoNotOverbookEvent`, который запускает
20 конкурентных запросов через `Task.Run` и `Task.WhenAll`.

## Формат ответа при ошибках

Все ошибки возвращаются в едином формате [Problem Details (RFC 7807)](https://datatracker.ietf.org/doc/html/rfc7807).
Необработанные исключения перехватываются глобальным middleware `ExceptionHandlingMiddleware`, ошибки логируются через `ILogger`.

| Статус | Когда возникает |
|---|---|
| `400 Bad Request` | Ошибки валидации: некорректное тело запроса, неверные параметры пагинации, `totalSeats` меньше единицы |
| `404 Not Found` | Событие или бронь с указанным идентификатором не найдены |
| `409 Conflict` | На событии не осталось свободных мест |
| `500 Internal Server Error` | Непредвиденная ошибка сервера |

Пример ответа при ошибке `404`:

```json
{
  "title": "Ресурс не найден",
  "status": 404,
  "detail": "Событие с идентификатором '11111111-1111-1111-1111-111111111111' не найдено."
}
```

При ошибках валидации (`400`) дополнительно возвращается объект `errors` со списком проблемных полей.

### Пример тела запроса на создание события

```json
{
  "title": "Встреча команды",
  "description": "Пиво в честь окончания первого спринта",
  "startAt": "2026-06-22T12:00:00",
  "endAt": "2026-06-22T13:00:00",
  "totalSeats": 20
}
```

Поля `id` и `availableSeats` заполняет сервер, присылать их не нужно — в контракте запроса их нет.

## Валидация

Для создания и обновления события действуют следующие правила:

- `title` — обязательное поле;
- `startAt` — обязательное поле;
- `endAt` — обязательное поле;
- `endAt` должно быть позже `startAt`;
- `totalSeats` — обязательное поле, значение должно быть больше нуля;
- при обновлении `totalSeats` не может быть меньше числа уже занятых мест.

Отсутствие обязательных полей ловит автоматическая валидация модели — ответ `400 Bad Request`
в формате Validation Problem Details со списком проблемных полей. Остальные правила проверяет
сам объект события в методах `Event.Create` и `Event.Update`: при нарушении бросается
`ValidationException`, которую middleware превращает в `400` в формате Problem Details.

## Тесты

Юнит-тесты написаны на xUnit и находятся в проекте `ProjectWork.Tests`.
Они покрывают CRUD-операции, фильтрацию, пагинацию, валидацию модели события,
создание броней, смену их статуса, работу с местами и неуспешные сценарии бронирования.

Отдельно проверяется поведение при конкурентных запросах: тесты запускают настоящий параллелизм
через `Task.Run` и `Task.WhenAll` и убеждаются, что при двадцати одновременных запросах
на событие с пятью местами создаётся ровно пять броней, а все идентификаторы уникальны.

Запуск всех тестов из корня репозитория:

```bash
dotnet test
```

## Особенности хранения данных

События хранятся в коллекции `List<Event>` под блокировкой, брони — в потокобезопасном
`ConcurrentDictionary<Guid, Booking>`. Оба хранилища живут в памяти приложения и зарегистрированы
как Singleton, поэтому данные общие для всех запросов, но после остановки или перезапуска
приложения удаляются.
